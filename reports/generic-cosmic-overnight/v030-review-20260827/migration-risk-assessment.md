# 新求解器架構：成果保留路徑與風險評估

日期：2026-08-27。本文記錄第六批結案後的成果保留建議與架構風險。使用者已選定下一步嘗試新架構，本次只更新文件；實作尚未開始。第六批實證見 [結果分析](review.md)，現行計畫見 [roadmap](../../../.agents/roadmaps/broad_solver_implementation_plan.md)。

## 結論

**你的擔心合理：若把既有規則改成候選、同時換成全新的評分器，第一版效果可能明顯低於 0.30。現有證據無法估計會掉多少，更不能保證完整移植。** 不過，原計畫不必變成從零重作：mechanics、objective、資源判斷、有限搜尋、兩個 Rust base engines 和大部分規則都可以保留。

建議將此方向切成能分別驗收的階段：**先換結構並檢查行為一致性，再換決策方式並檢查機率效果。** 結構階段在事先聲明的 corpus 上驗證舊能力完整承接；策略階段容許建議和個別勝負改變。

0.30 已由使用者接受為有足夠改善、保留局部小幅缺陷的研究 baseline。下一階段同時保留它的收益與已知代價，用於追蹤能力、診斷交互作用和比較新策略；Web 採用及正式發布仍有各自的 evidence review。

## 原計畫已經做對的事

最初設計保存在 [第六批歷史 brief](../../../.agents/archive/handoffs/overnight-v030-review-2026-08-27.md)，現行設計 owner 是 [roadmap](../../../.agents/roadmaps/broad_solver_implementation_plan.md)。分段計畫保留以下核心：

- Shadow 階段仍回傳 0.30 建議，先收集證據。
- 保留跨步路線意圖，分清暫時插入技能與正式換路線。
- 逐批拆出 producers，不一次移除兩個 base engines。
- 合併相同技能，不以來源票數加權；只對少量候選做有限續作比較。
- 最後才刪除舊決策流程，雙路徑不是永久產品架構。

因此需要補強的是**怎樣證明舊成果仍在，以及何時真的可以拿掉舊選擇順序**，不是推翻整份設計。

## 建議的實施順序

### 1. 凍結證據，不先凍結新策略

保留 0.30 binary／source checkpoint、完整第六批資料、0.22 比較基準及本次反例。建立能力清單，逐項連到成功案例、失敗案例、原 owner 和驗收方式。

把資料分成兩種用途：

- **回歸資料**：已看過的六批結果、這次 12 次完成損失和 14 次滿品質損失，用來追蹤既有能力與診斷失敗模式；策略改變時仍依整體機率效果判斷。這些資料已參與分析，與未見保留集分開管理。
- **新的保留集**：先固定未參與調整的 seeds 與測試條件，等本階段實作完成才看結果。全部 50 families 和 10 equipment 仍要覆蓋；不能把已經反覆研究的 family 改名為 unseen family。

風險設定會共用 paired seed；同一案例在三種 risk 下失敗不是三個獨立證據。統計區間應尊重這個配對／群集結構。

### 2. 先做能逐步對上的結構搬移

Shadow 回傳舊答案只能證明「觀測沒有干擾」，還不能證明新 producers 已完整承接能力。應再加一個明確里程碑：

**新資料流自己算出原本的選擇，獨立與凍結 0.30 比較。** 此時可以暫時保留舊規則優先序作為相容的仲裁方式；尚未宣稱共同 scorer 已有更好策略。

一致性至少包括：action、`GenericDecision.option/persona`、下一步 state、完整 planner context、RNG cursor、資源計數、停止原因、actions／steps 和終局結果。僅比最後完成率，或僅比當步 action，不足以驗收搬移。

原始 overnight rows 沒有逐步 trace；需要從 immutable binary 重播建立逐步 corpus。現有輸出中的 context fingerprint 也不是完整 context 序列，不能代替所有欄位的比對。

觀測／候選產生不得提前更新真實 context、消耗 RNG 或共用可變搜尋預算。只有玩家實際執行後才更新正式狀態；假想續作使用隔離副本。

### 3. 再讓新選擇器挑戰既有方案

每一步把既有方案作為明確參考候選，先比較替代方案和「照目前路線繼續」的結果。證據不足、預算耗盡或差距不具實際意義時，沿用參考方案。

比較的單位應是**首步技能及其後續路線**，不能只有當步品質增量。至少看見 setup 的 consumer、接下來的資源恢復與完工退路。有限 horizon 結束仍未完成時，用同一套已知 continuation 評估尾端，不把半成品的高品質直接當成完成收益。

這是減少退步的設計，不是數學上的不退步保證：替代方案會走進舊策略未到過的 state，回到舊策略也不能回復已花掉的資源或舊路線。近似評分、有限展開和假設球色模型仍可能選錯。

### 4. 每次只開放一類決策改變

先選一個有明確玩家收益、可用 state signal 辨識的範圍試行。其他 producers 可以提供 shadow 證據，但不一起改變輸出。不要同時重寫 objective、context、候選集合、評分權重與搜尋深度。

每批要看「候選缺席」與「候選存在但被選錯」兩種失敗。前者應修 producer，後者應修比較／續作估計；不能全部再加一個更高優先序的 override。

每批依 [驗收標準](../../../.agents/skills/domain/algorithm_verification.md) 預先固定主要效果、可接受代價、重要切片及不確定性處理。以 0.30 比較新策略的機率效果；0.22 與舊案例保留作歷史診斷。個別完成或滿品質損失可形成已知取捨，正確性及明示的 runtime 契約獨立驗收。

### 5. 最後才拿掉舊選擇順序

新流程通過聲明的結構一致性、保留集機率效果、重要切片、玩家偏離和 latency 驗收後，移除舊仲裁順序及 runtime 中的舊完整 policy。凍結 binary 留在離線 evidence，之後只維護採用的新決策流程。

如果新 scorer 尚未通過，停在「結構整理成功、行為未切換」也有價值：程式已更清楚，既有成果仍可用。沒有必要為證明架構方向而提前降低行為驗收標準。

## 原設計值得補上的五個細節

1. **同技能、不同路線不能把脈絡丟掉。** 合併 action 的 mechanics preview 很合理，但兩個來源可能帶來不同 consumer、resource reserve、context 更新。合併後仍應保存這些差異，等真正選定續作才決定下一個 intent。
2. **沒有找到完工證明，不等於已證明不能完工。** 現有 `deterministic_completion_first` 有 7 actions 呼叫和 4,096 展開限制，且使用 Normal continuation；其他搜尋也有自己的預算。證據需區分「找到路線／已反證／預算內未找到」。不能讓成本低的 producer 因證據較少就被錯判為 unsafe。
3. **資源數字較高，不一定全面優於另一個 state。** CP／耐久的 Pareto 排除要考慮 buff、condition、combo、一次性資源和 route context。語意不可比時，當成 trade-off，不做有保證的 dominance 宣稱。
4. **路線承諾不是沉沒成本。** 保護的是還能產生未來收益的 setup／consumer，不是「前面已花了很多，所以不能換」。保留遇到新 condition、失敗或玩家偏離時的退出條件。
5. **用實際能力收益衡量計算成本。** 目前 native 平均單步約 0.612ms；「新方案不到 3 秒」過於寬鬆。需要固定 work budget、候選數／展開數，以及品質、完成率、最差格、工序和目標裝置 latency 的共同改善。搜尋未完成時的回傳契約也要單獨驗證。

## 風險評估

等級是依目前程式與反例作的工程判斷，不是估算概率。

| 風險 | 直接全面改寫 | 採上述分階段路徑後 | 決策時應注意 |
| --- | --- | --- | --- |
| 初版效果明顯下滑 | 高 | 結構階段低；策略切換階段仍中至高 | 只有 exact parity 階段能用原行為作強保護，後續無全面保證 |
| 隱藏 context 語意遺失 | 高 | 中 | `option/persona` 和使用計數已直接影響選擇，需要完整資料比對 |
| 局部評分破壞長程路線 | 高 | 中 | 有 route intent 與 continuation 可減少，有限搜尋仍有盲區 |
| 新評分器成為另一組難維護權重 | 中至高 | 中 | 先用少量明確 constraints；沒有證據支持時不持續加權重 |
| 留下永久兩套 runtime | 中 | 低至中 | 預先定義刪除條件；移植期雙路徑與最終主／快速 solver 是不同概念 |
| 對六批資料過度調整 | 高 | 中 | 把舊資料當 regression，另設真正未看的保留集 |
| 工期超出預期 | 未知 | 中 | 第一階段可獨立交付；目前沒有足夠實作量測，不能承諾整體工期 |
| 真實遊戲或瀏覽器效果不符模擬 | 未知 | 仍未知 | 本次是 assumed-world native evidence；仍需遊戲實證及目標裝置量測 |

## 已選方向與下一次實作交付

使用者已選擇以 0.30 作研究 baseline，開始嘗試求解器基礎架構改動。本次只更新文件，程式實作留待後續 task；[roadmap](../../../.agents/roadmaps/broad_solver_implementation_plan.md) 是目前步驟與驗收的 owner。建議先交付能獨立驗收的能力對照、觀測及結構搬移，再逐類開放共同 scorer。

第一階段的交付應說明：

- 哪些能力已搬移、哪些仍由原 engine 提供。
- 新資料流在聲明 corpus 上的 action、context 與結果一致性。
- 已知收益及損失的可重播入口與用途。
- 觀測／整理成本，以及下一個可單獨試驗的 producer／route。
- 下一次策略實驗的主要效果、代價界線與停止條件。

0.30 的已知損失留作新架構的診斷材料，逐案修補不是開始前的必要步驟。結構搬移驗一致性；換策略驗機率效果、重要切片與成本。這樣既能追蹤能力是否漏搬，也能接受值得採用的勝負取捨。

新架構有機會減少「後加規則遮住前面規則」與短視切換，但不能保證擺脫所有局部最佳。若候選集合漏掉好路線，或有限 horizon 看不到 setup 回報，共同 scorer 一樣會受限。它的首要價值是讓失敗能被分辨、比較與維護；效果改善仍須由後續 evidence 證明。
